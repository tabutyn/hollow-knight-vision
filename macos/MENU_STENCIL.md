# Menu stencil tracker

The menu tracker builds 23 scene templates from the rectangles in the human
labeling store. For each non-selector object, up to eight captures are aligned
within a six-pixel translation search. Pixels survive only when at least 70%
of aligned captures contain stable, bright, low-chroma menu text there.
Animated backgrounds and isolated particles are discarded. The surviving
pixel extent defines both the stencil search box and its exact screen position.
Each object therefore uses one sparse consensus stencil instead of several
photographic background crops.

A focused draft may contain only the object that failed recognition. It does
not participate in scene or selector geometry, but its labeled pixels become
an additional masked object stencil on the next launch. This lets a small
correction improve one word without requiring the user to relabel the screen.

The human consensus remains the canonical probe and position. Full scene
validation can also compare a consensus from the latest clean live captures.
This gives changing headings and objects such as `Advanced Settings` a current
rendering without allowing one live frame to redefine the scene.

Select decorations use a separate consensus for each captured selected row.
Those stencils keep only stable decoration pixels and reject changing menu
background pixels. The established geometry remains the primary runtime path;
the measured screen-space position and combined consensus are the primary
runtime path. When that stencil is weak but selector pixels are present, the
tracker immediately compares the latest clean live variant at the same
position.

`menu-stencil-positions.json` is generated by a one-time exhaustive pass. For
every distinct captured selection state, it searches the complete 640×360
screen for every menu object and both selector decorations. Human rectangles
validate the result only after the search. Rejected searches remain recorded
for diagnosis and never override runtime geometry.

Normal runtime loads the bundled geometry, then overlays stable per-language
selector positions from the writable calibration. A development launch can
explicitly mirror those updates into the project resource with
`--menu-stencil-project-calibration=/path/to/menu-stencil-positions.json`.
The dashed search regions therefore follow the current frame offset immediately; changing their
base positions requires an explicit calibration run.

Live calibration uses the same clean 640×360 frame that enters Vision. Launch
with `--enable-automation-control`, move to a row through `control-game.sh`,
then save the recognized row with `menu-calibration-control.sh capture`. A row
that is not yet recognizable can be bootstrapped with an explicit context and
class identifier; the generator still rejects its position unless exhaustive
matching agrees with the human-derived row geometry or a confident left/right
selector pair occupies the same row.

Regenerate the catalog with:

```sh
HollowKnightVision --calibrate-menu-stencils \
  --menu-stencil-examples=/path/to/examples \
  --menu-stencil-calibration-output=/path/to/menu-stencil-positions.json
```

Runtime has two stages:

1. **Search:** compare one sparse, scene-specific probe from every menu set.
   Fully compare the consensus pixels only for the few probe candidates close
   to the winner. Full-probe validation prevents small shared words from
   admitting a scene on their own.
2. **Track:** compare the winning scene's probe, then scan every measured
   selector pair in that scene. This prevents a weak stale match at the old row
   from suppressing the newly selected row. Refresh the remaining objects in
   the current scene every 12 frames.

Object-model inference is skipped while a menu stencil is positively matched.
The models remain available as fallback while the stencil search is unresolved.

`Debug View > Menu Stencil Reference` draws only verified consensus pixels at
50% opacity inside their pixel-derived box. Green outlines pass, red outlines
fail, and thick yellow outlines show the matched selected-row decorations.
Blue dashed rectangles are the measured selector search regions for every row
in the solved menu. They stay visible and are the only positions used by the
runtime selector matcher. They remain visible during the brief probe-loss
grace frame. Inferred solid search boxes are no longer used.
